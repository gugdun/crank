# texture

A very thin wrapper around `LoadTexture` that lets the rest of the engine
treat textures as `{id, width, height, path}` records with a known
ownership story.

## Public API

```c
typedef struct {
    uint32_t id;
    int width;
    int height;
    char *path;
    Texture2D rl_texture;
} texture;

texture *tex_load(const char *path);
void tex_free(texture *tex);
```

## Loading

`tex_load(path)` appends `.png` to `path` and calls raylib's
`LoadTexture(path_png)`. If raylib returns an invalid texture, the
function frees its own buffers and returns `NULL`.

On success, it:

1. Sets `TEXTURE_WRAP_REPEAT` so wrapped diffuse coordinates tile.
2. Sets `TEXTURE_FILTER_BILINEAR`.
3. Calls `GenTextureMipmaps` for trilinear-style minification.
4. Copies the texture id / width / height into the wrapper struct.
5. Duplicates the requested path (without the `.png` suffix) into
   `tex->path` for later equality checks.

## Why a wrapper at all

The `mesh` module needs to associate textures with mesh surfaces, look
up loaded textures by their virtual path, and own/release them in
`mesh_free`. Doing that on the raw raylib `Texture2D` would require
storing parallel arrays. The `texture` struct keeps everything together
and gives the mesh module a single value-type to put inside its texture
array.

## Lifetime and ownership

`tex_load` returns a heap-allocated `texture *` that the caller owns.
`tex_free` calls `UnloadTexture` on the raylib texture, frees the path
string, and frees the wrapper. In practice the engine does not call
`tex_free` directly; the `mesh` module copies the texture struct
by-value into its own array and is responsible for unloading at
`mesh_free` time.

## Failure mode

The mesh builder treats a `NULL` return as "use the fallback texture".
The fallback is a 32x32 magenta-and-black checkerboard generated by the
mesh builder. There is no automatic retry, no substitute search path,
and no soft-fail to a default white texture beyond that.

## What this module does NOT do

- No support for non-PNG formats (no `.wal` parsing, despite the
  `wal_header` struct in the BSP header -- that struct is reserved for
  future use).
- No image processing (resizing, cropping, gamma correction).
- No de-duplication. Two `tex_load` calls for the same path produce two
  separate GPU textures. De-duplication happens one level up in the
  texture resource manager via path caching.
- No async loading. Loading is synchronous and blocks the main thread.
